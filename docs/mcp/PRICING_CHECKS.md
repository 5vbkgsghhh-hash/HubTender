# Проверки записи MCP — 16.10.2026

## Политика

Через `tenderhub_price_boq_item` записываются только `суб-раб` и `суб-мат`.
Комплексные типы не поддерживаются, в том числе как источник новой цены при
обновлении существующей строки. При создании копии обычные архивные `раб`/`мат`
записываются как `суб-раб`/`суб-мат`, сохраняя единицу и цену источника.
Существующая строка другого типа автоматически не переклассифицируется.
Создание карточки библиотеки через MCP также допускает только эти два типа.

Изменяемая строка обязана иметь номенклатурный ID с непустым названием,
совпадающую каноническую единицу, категорию затрат, положительные конечные
количество и цену. Материал требует расход >= 1; связанный материал — ещё
положительного перевода. Для доставки `суммой` обязательна сумма > 0.
Новая карточка/копия материала получает явные значения по умолчанию: расход 1,
доставка `в цене`, сумма доставки 0. Они показываются перед подтверждением.
Расход существующей строки через MCP по-прежнему не редактируется.

## Выбранные правила

Используются SQL из действующего серверного каталога, без отдельной реализации
порогов на стороне агента:

| Раздел CHECKS-GUIDE | Коды |
| --- | --- |
| 5.1 | A, AB, F, B, M, R, S |
| 5.2 | U, H, YD, Y |
| 5.3 | I, J |
| 5.4, без E и P | L, QA |
| 5.7 | AA, N |

Ошибки блокируют запись. Предупреждения и информация попадают в подтверждение
инженера. Кроме того, обязательные поля изменяемых строк проверяются жёстко:
например, новую строку без категории N или с нулевой ценой нельзя записать
даже после подтверждения. V и GA в этот набор не входят.

Проверяется целевая позиция целиком, включая ранее существовавшие строки.
SQL получает ограниченные входные отношения до агрегирования; для F также
включаются внешняя родительская работа и её позиция. Весь тендер не сканируется
отдельно каждым правилом.
Ошибку в ней нужно исправить до следующей записи MCP. Замечания других
позиций не блокируют работу. Выключенное выбранное правило или ошибка SQL
означают отказ проверки, а не успешное прохождение.

Исключение E из набора не отключает действующее расчётное ядро: попытка
пересчитать валютную строку без курса по-прежнему откатывается с MISSING_FX_RATE.

## Практический порядок

1. Клиент читает исходную цену/source_version, целевую строку/ETag и ревизию.
2. Если Количество ГП отсутствует, инженер явно передаёт `position_quantity`.
   Оно не копируется из объёма заказчика. Это вход для позиции, а `quantity`
   остаётся количеством работы или непривязанного материала.
3. Сервер выполняет предполагаемую запись и пересчёт в транзакции, которая
   всегда откатывается. Нет сохранённых строк, аудита, источников или квитанций.
4. При ошибках подтверждение не запрашивается. В остальных случаях инженер
   видит количества, точную цену, коэффициенты, сумму строки, итог позиции и
   найденные предупреждения, а при изменении ГП — старое и новое значение.
5. Подтверждение связано с аргументами, версией каталога и полным снимком
   рассчитанных строк/полей позиции, названиями и единицами номенклатуры.
   Старое ГП также входит в снимок. При изменении данных нужно подтвердить
   новый результат. Для клиентов без elicitation работает confirmation_state.
6. При записи те же правила повторяются внутри блокировок и одной транзакции.
   Ошибка или изменившийся снимок откатывают всё, включая Количество ГП,
   связанные материалы, ревизию, аудит и квитанцию.
7. Подтверждённый повтор request_key возвращает старую квитанцию и не создаёт
   строк повторно. Клиент затем читает фактические данные обратно.

## Выкладка и границы

Нужна миграция `2026_10_mcp_pricing_ownership.sql` и обновлённый backend с ранее
установленными direct-pricing/catalog миграциями. Нового OAuth scope нет. MCP_WRITE_ENABLED
и разрешения пользователя продолжают применяться. Схема существующих клиентов
совместима; для позиций без Количества ГП теперь нужен position_quantity.

## Принадлежность расчёта

У расчёта позиции один владелец. Первое подтверждённое добавление в пустую
позицию закрепляет её за инженером; preview этого не сохраняет. Другой
пользователь не может менять, дополнять или удалять этот расчёт, менять ГП,
очищать позицию либо обходить ограничение через импорт, восстановление,
массовое удаление или каскадное удаление тендера. Повышенная роль не даёт
исключения. Чтение и использование чужого расчёта как источника копии разрешены.

Защита стоит на сервере в транзакционных триггерах. JWT/API-key middleware
передаёт проверенного автора в БД; поля тела запроса не заменяют его.
Владение сохраняется после очистки/удаления для безопасного восстановления.
Привилегированные фоновые расчёты и обслуживание без делегированного пользователя
остаются доверенной границей, недоступной через MCP/API.

Старые позиции атрибутируются по первому INSERT-аудиту или автору импорта,
а не последнему редактору. Неизвестные/смешанные авторы блокируют запись до
явного назначения владельца оператором после проверки истории. Для уже
удалённых расчётов используется исходный INSERT-аудит. Автоматического
«забрать себе» в MCP нет. До выкладки см. `OWNERSHIP.md`.

Количество ГП и примечание имеют отдельный атомарный аудит старого/нового
значения с автором; MCP добавляет request_key. Отказ/preview не оставляют аудит,
повтор квитанции не создаёт второй записи.

Проверки выполнены на отдельном PostgreSQL 17 и через настоящий HTTP MCP SDK.
Продакшен не использовался для тестовых записей. Перед выкладкой нужен staging
прогон на рабочих объёмах данных и совместимость с инженерным MCP-клиентом.

Общий `tenderhub_get_pricing_qa_report` остаётся прежней базовой сводкой.
Полный набор 17 проверок в этой доработке применяется к операции записи,
а не подменяет всю страницу «Проверка данных».
