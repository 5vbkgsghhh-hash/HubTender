# Ревью проверок MCP — 16.10.2026

База: `origin/main` / `5beefd8`. Изменения относятся к прямой записи MCP и
созданию карточек библиотеки через MCP. После повторного ревью добавлена
защита владельца, охватывающая также обычные серверные пути записи/удаления.
Разметка UI не менялась.

## Исправлено при ревью

1. Подтверждение, связанное только со списком замечаний, пропустило бы изменение
   количества ГП с 10 на 11, если оба значения не вызывают замечаний. Отпечаток
   теперь включает полный предполагаемый снимок позиции и строк. Исключены
   сгенерированный ID новой строки и служебные timestamps, чтобы повторная
   проверка того же предложения давала тот же результат.
2. Комплексный источник мог бы попасть в обновление существующей суб-строки,
   хотя создание новой комплексной строки было запрещено. Источники комплексных
   типов теперь отклоняются в обоих путях.
3. Пересчёт работы может затронуть старого дочернего материала из другой позиции.
   Такой случай теперь откатывает всю операцию как F, даже если устаревшая БД
   содержит историческую связь, предшествующую составным FK.

## Подтверждено тестами

- Набор содержит ровно 17 выбранных активных правил, без E, P, V и GA.
- Предварительный расчёт не сохраняет строки, аудит, квитанции, ГП или ревизию.
- U блокирует отсутствие ГП; явное position_quantity позволяет завершить запись.
- Изменяемая строка без цены, единицы, категории или с комплексным типом отклоняется.
- A, AB, I и L в существующих строках целевой позиции блокируют новую запись.
  После отказа количество строк, квитанций и финансовая ревизия не меняются.
- Работа пересчитывает материал и итоги позиции; результат проходит A/AB/I/J.
- Ручное quantity связанного материала отвергается.
- R требует подтверждения; изменение набора замечаний отменяет старое согласие.
- Изменение ГП без новых замечаний тоже отменяет старое согласие.
- Настоящий HTTP MCP-клиент без elicitation получает S в тексте подтверждения;
  до согласия ревизия не меняется, после — запись проходит.
- Повтор request_key возвращает квитанцию без дублирования записи.
- Карточки MCP допускают только суб-раб/суб-мат, расход >= 1 и положительную
  стоимость доставки для типа «суммой».
- Прежние сценарии источников/source_version, конкурентной записи, OAuth,
  создания библиотеки и восстановления квитанций проходят.

## Исправления повторного ревью

Проверены четыре дефекта первоначального коммита `f8b4648`:

1. **Чужая правка/удаление.** У позиции постоянный владелец. Триггеры БД
   проверяют проверенного пользователя BFF на вставке, правке, удалении,
   очистке, импорте, восстановлении, удалении позиции и каскаде тендера.
   Роли не обходят правило; пустая после очистки позиция сохраняет владельца.
   Исторически неизвестные/смешанные авторы блокируются до решения оператора.
2. **Устаревшее согласие после переименования.** Снимок содержит названия и
   единицы номенклатуры; строки справочника заблокированы до конца транзакции.
   После переименования прежний отпечаток отвергается, новый принимается.
3. **Аудит ГП.** Отдельный атомарный аудит сохраняет старое/новое ГП,
   примечание, пользователя и MCP request_key. Старое ГП включено в согласие.
   Preview/отказ не сохраняют аудит; replay не дублирует его.
4. **Задержка на большом тендере.** Входы 17 SQL ограничены целевой позицией
   до агрегатов. Внешние родитель и его позиция включены для F. Сравнение
   всех 17 результатов с исходным каталогом на синтетической ошибочной связи
   прошло. Деловые пороги каталога не копировались/не менялись.

Повторный прогон на отдельном PostgreSQL 17, localhost:55448:

```powershell
go test -p 1 -buildvcs=false -tags=integration ./internal/repository ./internal/services ./internal/mcpserver ./internal/mcpauth -run 'Boq|Import|Template|Copy|Clone|Transfer|PricingOwnership|DirectPricingScoped|Catalog|DirectPricing|AuthenticatedHTTP|OAuth|MCPPricing' -count=1 -json
```

**158 PASS, 4 SKIP, 0 FAIL.** Четыре прежних SKIP явно помечены в исходных
тестах: lineage переноса, даты источника в импорте и два списка отложенных
кейсов/instrumentation. Они не засчитаны как проверенные.
Есть проверки подмены helper-поля автора при другом проверенном контексте,
неизвестного автора, восстановления чужого аудита и повторного применения
миграции с известным/смешанным/неизвестным/удалённым расчётом.

Обычные тесты затронутых пакетов (middleware/apierr/pricing/quality/repository/
services/mcpserver/handlers), `go vet` этих пакетов и сборка `cmd/server` также
завершились успешно. Структурный read-only verifier новой миграции прошёл;
он не заменяет staging-проверку конкретной runtime-роли.

Локальный замер одного предложения: baseline 125,6 мс; при добавлении 50 000
посторонних BOQ-строк — 244,9 мс. До исправления на том же типе fixture было
1768,7 мс (baseline 105,5 мс). Это единичные локальные замеры, не SLA и не
результат production-нагрузки. Тендерная блокировка на время preview сохранена.

## Оставшиеся границы

- Не проверялись production-выкладка и нагрузка на реальном рабочем тендере.
- Обязательна новая миграция владения, разбор старых неоднозначных авторов
  и совместимый BFF. Порядок и права runtime-роли описаны в `OWNERSHIP.md`.
- Доверенные фоновые операции/оператор БД остаются привилегированной границей.
- Старые ошибки в целевой позиции блокируют её последующие записи MCP; обычная
  страница портала остаётся доступна для исправления исходных данных.
- Общий базовый QA MCP не стал полным отчётом страницы «Проверка данных».
